# リテンション検証計画と指標定義

対象: 白地図マインスイーパ / ランキング機能(Phase 2)着手前の検証ゲート

## 背景 (premortem レビューの反映)

「ランキング実装 → リテンション向上」は未検証の仮説である。地理学習ゲームは通常
「コンテンツ量」と「継続プレイ理由」が先であり、プレイヤー数が少ない段階のランキングは
価値を生まない。そこで **ランキング(Firebase)は保留**とし、先に
「なぜユーザーが翌日も戻ってくるのか」をローカル計測で検証する。

## 1. USP の確定

主役は **「本物の地図がそのまま盤面になるマインスイーパ」**(パズルが主役)。
「地理が学べる」は自然に付いてくる副次価値として扱い、コピー・UIの主語にしない。
市場は当面 **日本市場に集中**。英語圏展開は世界地図モードの完成度が上がるまで優先度を下げる。

## 2. 学習進捗の定義

成長指標は以下の優先順で定義する(すべて `src/lib/playStats.ts` で計測済み):

| 優先 | 指標 | 定義 | データ源 |
| --- | --- | --- | --- |
| 主 | 開放コレクション | マップごとの「一度でも開放した地域」のユニーク数(例: 47都道府県中32県) | `openedCodes` |
| 副 | マップ別クリア数 | mapId×難易度ごとのクリア回数 | `maps[key].clears` |
| 副 | クリア率 | clears / plays (適正帯 30〜70% を難易度調整の目安とする) | `totals` |
| 参考 | 継続日数 | プレイした日付のユニーク数・直近7日のプレイ日数 | `playDates` |

「未クリア地域コレクション」機能はこの主指標(開放コレクション)の可視化であり、
ランキングより先に実装する候補とする。

## 3. 計測項目と実装

`src/lib/playStats.ts`(localStorage、外部送信なし)が終局ごとに記録する:

- プレイ回数 / クリア回数 / ゲームオーバー回数(全体・マップ×難易度別)
- 合計・平均プレイ時間、マップ×難易度別ベストタイム
- プレイ日(YYYY-MM-DD のユニークリスト → 継続日数・直近7日を算出)
- マップごとの開放済み地域コード(ユニーク)

閲覧方法: ブラウザのコンソールで `hakuchizuStats()` を実行すると、サマリー+生データのJSONが得られる。
テスター(知人・家族)にはこのJSONの共有を依頼する。サイト全体のトラフィックは
Vercel Analytics(無料枠)を併用する。

## 4. ランキング(Phase 2)着手の判断ゲート

計測開始から **2〜4週間** 後に以下を確認し、満たす場合のみ Firebase ランキングを有効化する:

1. **再訪の実在**: テスター5名以上のうち過半数が「2日以上プレイ」(playDates ≥ 2)
2. **タイム意識の実在**: 同一マップ×難易度の再プレイ(記録更新挑戦)が観測される
   (`maps[key].plays ≥ 3` のキーが存在する)
3. **クリア率が適正帯**: 全体クリア率 30〜70%(低すぎ=難しすぎて競う以前、高すぎ=作業化)

ゲートを満たさない場合は、ランキングではなく
**学習進捗可視化(開放コレクション画面)** と **人気マップ(topMaps)へのコンテンツ追加** に投資する。

## 5. 潜在的欠陥への対応方針

| 指摘 | 対応 |
| --- | --- |
| Firebase 読み取り回数の過小評価 | Phase 2 着手時に閲覧頻度を本計測値から再見積もり。既定で「クリア画面でのみ取得(自動ポーリングなし)」+ 超過前に上位N件の1ドキュメント非正規化へ移行 |
| 匿名ユーザー名の重複 | 表示名の一意性は保証せず、UID下4桁を「name#a1b2」形式で併記して識別する(Phase 2 実装時) |
| チート対策不足 | ルール検証(値域・自己ベストのみ更新)+ 明らかな外れ値(理論最短未満)の非表示フィルタ。完全防止はコスト対効果が合わないため追わない |
| 雑学データ作成コスト | 人気マップ(topMaps)上位から優先的に追加し、全マップ網羅を目標にしない |
| モバイル地図操作UXの複雑化 | 新機能はゲーム盤面へのオーバーレイ追加を避け、クリア画面・別画面に隔離する(本計測も操作系に一切触れていない) |
